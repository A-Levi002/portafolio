01 — Problema

La brecha entre el incidente
y la respuesta coordinada

En comunidades urbanas con actividad industrial, los incidentes ocurren en segundos pero la respuesta tarda minutos o no llega coordinada. Ese intervalo es el problema que app-security ataca.

"Los ciudadanos que presencian o sufren emergencias — vertidos de materiales peligrosos, delitos, ataques, incidentes ambientales — no tienen un mecanismo rápido y efectivo para reportar lo ocurrido, recibir orientación sobre qué hacer y lograr un despacho coordinado de unidades de emergencia. Esto resulta en respuestas lentas o inadecuadas, materiales peligrosos no gestionados correctamente y posible contaminación ambiental."

— Situacion problematica identificada / ODS 12

01 / 03

Materiales peligrosos sin gestionar

Zonas industriales urbanas generan residuos y derrames que los ciudadanos no saben cómo reportar ni cómo manejar. Sin un canal directo a una unidad química especializada, el material permanece sin atención y contamina el ambiente.

ODS 12.4 / 12.5
02 / 03

Despacho descoordinado de unidades

Sin triaje previo, las centrales de emergencia no saben si enviar una patrulla, una ambulancia o una unidad química. Esto genera duplicación de recursos, demoras o envío de la unidad incorrecta al incidente.

RF3 — Despacho coordinado
03 / 03

Ciudadano sin orientacion inmediata

Mientras se espera la respuesta de emergencia, el ciudadano no sabe qué hacer: si alejarse, si administrar primeros auxilios, si cerrar el área. La falta de orientación en los primeros minutos puede agravar la situación.

Seguridad

Autenticacion y aislamiento de datos

Autenticacion con email y clave via Supabase Auth. Row Level Security (RLS) en todas las tablas de Postgres. Cada Edge Function valida el JWT antes de procesar la solicitud.

Rendimiento

Respuesta en menos de 5 segundos

Tiempo de respuesta del sistema menor a 3 segundos. Triaje IA en menos de 5 segundos. maxOutputTokens reducido de 2048 a 1024. Cache de respuesta con TTL de 3 minutos para consultas repetidas.

Disponibilidad

Modo offline parcial

El catalogo de lugares cercanos y los protocolos de actuacion ante materiales peligrosos estan disponibles sin conexion. El ciudadano puede consultar qué hacer incluso si no tiene datos.

Usabilidad

Interfaz de emergencia directa

Boton SOS accesible desde cualquier pantalla. Chat conversacional con la IA. KeyboardAvoidingView para Android para evitar que el teclado tape el campo de texto en situaciones de estres.

Escalabilidad

Arquitectura horizontal

Edge Functions de Supabase escalan horizontalmente sin configuracion adicional. Supabase Realtime gestiona actualizaciones en vivo para multiples ciudadanos y unidades de emergencia simultaneos.

Mantenibilidad

Modulos compartidos y tipado estricto

Carpeta _shared centraliza la logica de IA, clientes de Supabase y headers CORS. TypeScript en todo el stack. Cada Edge Function tiene responsabilidad unica y puede actualizarse de forma independiente.

Patron — Fallback de IA

Gemini primario, OpenRouter como respaldo

La capa de IA en _shared/ai.ts intenta primero Gemini 3.6 Flash via LangChain. Si recibe error 429 (cuota agotada), ejecuta runWithProviderFallback que redirige la solicitud a OpenRouter con el modelo inkling:free. El frontend no percibe el cambio de proveedor.

Patron — Modulos compartidos

_shared evita duplicacion entre funciones

Las 9 Edge Functions comparten logica a traves de la carpeta _shared. Esto significa que un cambio en la capa de IA, en la configuracion de CORS o en el cliente de Supabase se aplica a todas las funciones sin tocar cada una individualmente. Reduce superficie de errores y deuda tecnica.

Patron — Seguridad por capas

RLS + JWT + Edge Function auth

El aislamiento de datos ocurre en dos niveles. En la base de datos, las politicas RLS de Postgres garantizan que cada usuario solo lee y escribe sus propios registros. En el backend, cada Edge Function extrae y verifica el JWT del header Authorization antes de ejecutar cualquier consulta.

Patron — Dirigida por eventos

Realtime para actualizaciones en vivo

Los canales de Supabase Realtime propagan cambios en tablas clave (reportes, notificaciones) a todos los clientes suscritos mediante WebSocket. Esto elimina la necesidad de polling desde el frontend y reduce la latencia percibida en el flujo de despacho de unidades.

Nivel 2 — Containers Procesos, stores y sus comunicaciones

La app React Native se comunica con cada Edge Function a traves de HTTP. Cada funcion es un contenedor independiente con una responsabilidad unica. La base de datos Postgres es el store central; Realtime actua como bus de eventos para propagar cambios en tiempo real al frontend sin polling.

Store central con RLS. Realtime propaga INSERT/UPDATE en reportes y notificaciones a todos los clientes suscritos.

Nivel 3 — Component: AI Chat Triage Flujo interno del componente de triaje

El componente de triaje IA es el nucleo del sistema. Cada mensaje del ciudadano desencadena un analisis contextualizado: no se evalua solo el mensaje actual sino el historial completo de la conversacion junto con la evidencia multimedia adjunta. La decision de triaje es incremental y se refina en cada turno.

_shared/ai.ts — runChatTriage 
// Entrada por turno
INPUT  {
  categoria:  "ambiental" | "medica" | "criminal",
  historial:  Message[],          // conversacion completa
  evidencia:  File[] | null,      // foto / video / audio
}

// PASO 1: construccion del prompt
prompt = buildPrompt(systemPrompt, historial, evidencia)

// PASO 2: llamada al modelo primario
try {
  response = await geminiFlash.invoke(prompt, {
    thinkingConfig: "LOW",
    maxOutputTokens: 1024,
    schema: TriajeZodSchema,     // salida estructurada
  })
} catch (e) {
  if (e.status === 429) {
    // cuota agotada — conmuta a OpenRouter
    response = await runWithProviderFallback(prompt)
  }
}

// Salida estructurada
OUTPUT {
  triage:       "sin_riesgo" | "dudoso" | "emergencia",
  unidad:       "patrulla" | "ambulancia" | "quimico",
  base:         string,
  eta_minutos:  number,
  severidad:    "baja" | "media" | "alta" | "critica",
  tipo_respuesta: string,
  recomendaciones: string[],
}

06 — Metodologia

Boehm–Turner y Cockburn
aplicados en 4 iteraciones

El modelo de equilibrio de Boehm y Turner, combinado con la rejilla de Cockburn, orienta proyectos donde los requisitos son incompletos al inicio y el equipo es pequeno. Ambas condiciones aplican a app-security.

Iteracion 1

Base funcional

Login y registro con email y clave. Perfil basico del ciudadano. Catalogo offline de lugares cercanos y protocolos de actuacion disponible sin conexion a internet. Navegacion principal con BottomNavBar.

Iteracion 2

IA y despacho

Chat de emergencias con triaje IA usando Gemini 3.6 Flash y LangChain. Salida estructurada via Zod. Despacho operativo de unidades (patrulla, ambulancia, quimico) con base, ETA y tipo de respuesta.

Iteracion 3

Modulos completos

Modulo ambiental para materiales peligrosos (ODS 12). Mapa con marcadores de incidentes. Contactos de confianza con notificacion automatica. Fallback de IA a OpenRouter con runWithProviderFallback.

Iteracion 4

Optimizaciones y portafolio

Reduccion de maxOutputTokens de 2048 a 1024. Cache de respuestas con TTL de 3 minutos. KeyboardAvoidingView para Android. Migracion de marca SECURE_OS a app-security. Tests unitarios: 15/15 pasando. Documentacion y portafolio.

Consumo y Produccion Responsables

En zonas urbanas con actividad industrial, los incidentes de materiales peligrosos son una externalidad frecuente y subatendida. La ausencia de un canal de reporte rapido significa que vertidos quimicos, derrames industriales y residuos peligrosos permanecen sin atencion durante horas. El modulo ambiental de app-security cierra esa brecha conectando al ciudadano directamente con una unidad quimica especializada, reduciendo el tiempo de contencion y el impacto ambiental de cada incidente.
